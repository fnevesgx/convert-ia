## 1. Contexto e objetivo

Tela mais usada da operação comercial: registra pedidos de venda com cliente e data de entrega. Quando concluído, o vendedor cria pedidos no sistema novo com o mesmo resultado do legado — mesmo número sequencial, mesmas validações — sem perceber diferença de comportamento, apenas de interface.

## 2. Comportamento atual — verdade do código

O fluxo parte de TEL-0032 (`/pedidos/novo`, servida por OBJ-0014/PPedidoNovo): o vendedor informa `cliente_id` (obrigatório) e `data_entrega` (opcional). No evento Salvar, PPedidoNovo valida cliente ativo (RN-01) e data não retroativa (RN-02) antes de chamar OBJ-0015/TPedido, que atribui o número sequencial por empresa a partir da tabela de controle PEDCONTROLE (RN-03) e persiste em PEDIDO/PEDIDOITEM. Sucesso navega para TEL-0033 (confirmação) com a mensagem "Pedido NNNNN criado"; data retroativa permanece em TEL-0032 com mensagem de erro (capturado em TC-TEL-0032-02).

### Controles (fonte × UI)

Cruzamento de `controles[]` (OBJ-0014) com `rotulo_ui`/`nome_fonte` do catálogo (TEL-0032). Fonte manda; UI é evidência. `Divergência` = `sim` quando ambos existem e diferem após normalizar espaços/case.

| Nome técnico | Descrição (fonte) | Rótulo UI | Tipo | Divergência |
|---|---|---|---|---|
| PedClienteId | Cliente | Código do Cliente | edit | sim |
| PedDtaEntrega | Data de entrega | Data de entrega | edit | não |
| GridItens.PedItemQtd | Quantidade | Qtd | grid_column | sim |
| BtnSalvar | Confirmar | Salvar | button | sim |
| BtnCancelar | Cancelar | Cancelar | button | não |

## 3. Relato da área usuária

A supervisora comercial relata que pedidos para cliente **inadimplente** (situação diferente de inativo) às vezes precisam ser liberados com autorização do gerente — hoje isso é feito alterando o status do cliente direto no banco e revertendo depois. Não há tela para esse fluxo no legado. Relato registrado como regra candidata (ver RN-04 na seção 6); decidiu-se não incluir neste item (seção 10).

## 4. Decisão de triagem

`converter`. Fluxo crítico de operação diária, alto volume, sem indício de regra morta. A modernização de aparência fica por conta do design system novo; o comportamento é preservado (diferenças deliberadas na seção 5).

## 5. Comportamento esperado — pós-conversão

Permanece: todas as validações (RN-01, RN-02), a numeração sequencial por PEDCONTROLE (RN-03), a navegação para confirmação em caso de sucesso e a convenção de dados da seção 7.

Componentes aplicados conforme `design_system_ref` (frontmatter) — protótipo do formulário de pedido no design modernizado, não o `design_system.tokens` do catálogo (esse último descreve a UI atual do legado).

Diferenças deliberadas em relação ao legado — **qualquer outra divergência é bug**:

1. Erro de data retroativa aparece inline no campo `data_entrega` (componente de formulário do DS novo), em vez de mensagem no topo da tela.
2. A confirmação (TEL-0033) vira toast + redirecionamento para a lista de pedidos; a tela intermediária de confirmação deixa de existir. O conteúdo da mensagem ("Pedido NNNNN criado") permanece idêntico.
3. Seleção de cliente por busca com autocomplete em vez de digitação do código numérico — o valor submetido continua sendo o mesmo `cliente_id`.

## 6. Regras de negócio

| ID | Regra | Origem | Decisão |
|----|-------|--------|---------|
| RN-01 | Pedido só é gravado se o cliente estiver ativo (`CLIENTE.CLISTATUS = 'A'`) | OBJ-0014 | manter |
| RN-02 | Data de entrega não pode ser retroativa; vazia assume a data do dia | OBJ-0014 | manter |
| RN-03 | Número do pedido é sequencial por empresa via PEDCONTROLE, não autoincremento | OBJ-0015 | manter |
| RN-09 | Job noturno fatura pedidos com entrega no dia e atualiza `PEDIDO.PEDSTATUS` | OBJ-0022 | manter (vale dos dois lados — ver seção 7) |
| RN-04 | Pedido para cliente inadimplente exige liberação do gerente | relato (seção 3) | ajustar — fora deste item, ver seção 10 |

## 7. Dados

Base compartilhada com o legado durante toda a convivência; nenhuma mudança de schema é necessária neste item.

- Mapeamento: `PEDIDO` → model `Pedido`, `PEDIDOITEM` → `PedidoItem`, `CLIENTE` → `Cliente` (leitura). `PEDCONTROLE` é lida/escrita via a mesma lógica de sequencial do legado — não substituir por sequence do banco enquanto o legado emitir pedidos.
- Convenções herdadas a respeitar: `PEDDTAENTREGA` vazia é gravada como data mínima do legado, nunca `NULL`; integridade `PEDIDO → CLIENTE` é garantida na aplicação (não há FK no banco — deliberado).
- Quem mais escreve nas tabelas: OBJ-0022/PFaturamentoNoturno (job, meia-noite) atualiza `PEDIDO.PEDSTATUS` (RN-09). O sistema novo não pode assumir que o status que gravou permanece; qualquer cache/estado local precisa tolerar essa escrita externa.
- Mudanças de schema: nenhuma. (Se fosse necessária, seria aditiva — ver princípio 2 do `CLAUDE.md`.)

## 8. Critérios de aceite

- [ ] Criar pedido com cliente ativo e data futura resulta em pedido persistido com número sequencial correto e toast "Pedido NNNNN criado".
- [ ] Data retroativa bloqueia o salvamento com erro inline no campo, sem persistir nada.
- [ ] Cliente inativo bloqueia o salvamento com a mesma mensagem do legado.
- [ ] Pedido criado no sistema novo aparece corretamente no legado (mesma base) e é faturado normalmente pelo job noturno.
- [ ] Data de entrega vazia assume a data do dia, gravada na convenção do legado (data mínima, não NULL).
- [ ] Rótulos exibidos batem com a coluna «Rótulo UI» da seção 2 (captura estágio 4); divergências fonte×UI listadas ali não são “corrigidas” espontaneamente — só mudam se constarem na seção 5.

## 9. Testes de caracterização

Caminho padrão: cenários derivados das regras da seção 6, automatizados no sistema novo. Onde há `casos_replay` real no catálogo, a coluna Origem marca `replay`; senão, `regra`.

| Cenário | Passos / entrada | Resultado esperado | Regra | Origem |
|---------|------------------|--------------------|-------|--------|
| TC-01 | cliente ativo `4471`, `data_entrega` futura, Salvar | Pedido persistido com número sequencial; toast "Pedido NNNNN criado" + lista (diferença 2 da §5) | RN-03 | regra (+ replay TEL-0032-01 como evidência) |
| TC-02 | `data_entrega` retroativa, Salvar | Nada persistido; erro inline em `data_entrega` (diferença 1 da §5) | RN-02 | regra (+ replay TEL-0032-02) |
| TC-03 | cliente inativo, Salvar | Bloqueia com a mesma mensagem de negócio do legado; nada persistido | RN-01 | regra |
